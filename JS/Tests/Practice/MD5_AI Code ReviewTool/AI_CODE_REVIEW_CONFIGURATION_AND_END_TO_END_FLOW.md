# AI Code Review — Configuration and End-to-End Flow

## 1. Purpose

This document is the practical configuration and interview-reference guide for the AI Code Review utility.

It explains:

- What was configured.
- Where each configuration is located.
- What each component does.
- How GitHub Actions drives the complete process.
- How the Gemini API key is supplied securely.
- How the Pull Request diff reaches the AI model.
- How the AI response becomes a review result.
- How the result is published and enforced through the quality gate.

The current supplied implementation is Gemini-based. The architecture also defines a provider-neutral design that can support OpenAI or another LLM.

---

## 2. High-Level End-to-End Flow

```text
Developer
    |
    | Creates / updates Pull Request
    v
GitHub Pull Request
    |
    | pull_request event
    v
GitHub Actions Workflow
    |
    +--> Checkout repository
    |
    +--> Read CODE_REVIEW.md
    |
    +--> Get PR metadata
    |
    +--> Calculate BASE_SHA / HEAD_SHA
    |
    +--> Generate PR diff
    |
    v
Node.js Review Logic
    |
    +--> Build review prompt
    |
    +--> Read GEMINI_API_KEY from environment
    |
    v
Gemini API
    |
    +--> gemini-3.6-flash
    |
    v
Gemini Review
    |
    v
Review Result Processing
    |
    +--> Severity counts
    +--> Recommendation
    |
    +--------------------+
    |                    |
    v                    v
PR Comment          HTML / Email
    |
    v
Quality Gate
    |
    +--> APPROVE           -> PASS
    |
    +--> CHANGES REQUESTED -> FAIL
    |
    +--> Invalid/missing   -> FAIL
```

The architecture document identifies GitHub Actions as the component responsible for triggering the workflow, checking out code, obtaining PR metadata, reading review rules, preparing the diff, supplying secrets, publishing results, and passing/failing the workflow.

## 4. GitHub Repository Configuration

### 4.1 GitHub Actions workflow

The workflow is located under:

```text
.github/workflows/code-review.yml
```

This workflow is the orchestration layer.

It tells GitHub:

1. When to execute the review.
2. Which runner to use.
3. How to obtain the repository.
4. How to prepare the Pull Request diff.
5. How to invoke the Node.js review logic.
6. Which secrets are available to the required steps.
7. How to publish the result.
8. How to enforce the quality gate.

### 4.2 Pull Request events

The current workflow uses:

```text
pull_request:
  opened
  synchronize
  reopened
```

Meaning:

- `opened` — review starts when a new PR is created.
- `synchronize` — review runs again when new commits are pushed to the PR.
- `reopened` — review runs again when a closed PR is reopened.

This makes the review part of the Pull Request lifecycle rather than a manually executed process.

## 5. GitHub Actions Permissions

Repository Actions permissions are important because the workflow needs to perform operations such as reading repository content and publishing the review.

When troubleshooting a workflow that does not start or cannot perform an operation, check:

```text
Repository
  -> Settings
  -> Actions
  -> General
```

Also check the permissions configured in the workflow itself where applicable.

The troubleshooting guide identifies repository Actions permissions and branch protection rules as items to check when the workflow does not start.

## 6. Gemini API Key Configuration

### 6.1 Where the API key is configured

The Gemini API key is stored as a GitHub Actions repository secret:

```text
GEMINI_API_KEY
```

The important concept is:

```text
GitHub Repository
    |
    v
Settings
    |
    v
Secrets and variables
    |
    v
Actions
    |
    v
GEMINI_API_KEY
```

The key is NOT supposed to be hard-coded in the JavaScript source.

### 6.2 How the key flows at runtime

```text
GitHub Secret
     |
     v
GitHub Actions environment
     |
     v
Node.js process
     |
     v
GEMINI_API_KEY
     |
     v
Gemini API request
```

The Gemini implementation documents that the API key is supplied through the GitHub Actions environment and sent to Gemini using the `x-goog-api-key` header.

### 6.3 Security rules

Never:

- Commit the API key to Git.
- Put the API key directly in source code.
- Print the API key in workflow logs.
- Put the API key into an AI prompt.
- Publish the key in a PR comment.
- Include the key in an artifact.
- Print authorization headers.

If a key is exposed, rotate/revoke it immediately, review logs and artifacts, replace the GitHub Secret, and restrict the replacement key according to the provider's current guidance.

## 7. CODE_REVIEW.md Configuration

`CODE_REVIEW.md` is the repository-level review policy.

It tells the AI reviewer what should be inspected and what constitutes an actionable issue.

The workflow reads the review rules from the Pull Request base commit.

Conceptually:

```text
Repository
    |
    +--> CODE_REVIEW.md
              |
              v
       Review Instructions
              |
              v
       AI Review Prompt
```

The review rules are therefore separated from the application code.

### Why is CODE_REVIEW.md excluded from the PR diff?

Because it contains review instructions rather than the application changes that the AI is expected to review.

The workflow also excludes the review workflow itself so that the review remains focused on application changes.

---

## 8. BASE_SHA and HEAD_SHA

The workflow uses:

```text
BASE_SHA
HEAD_SHA
```

These provide deterministic boundaries for the Pull Request diff.

Conceptually:

```text
BASE_SHA ----------------------> HEAD_SHA
    |                                |
    |<------ changed code ---------->|
```

The generated diff is the primary application input to the AI reviewer.

This is better than sending the entire repository because the AI should primarily review the code changed by the Pull Request.

---

## 9. PR Diff Preparation

The workflow:

1. Checks out the repository with full history.
2. Determines the PR base revision.
3. Determines the PR head revision.
4. Generates the difference between those revisions.
5. Excludes review instructions.
6. Excludes the review workflow itself.
7. Limits the diff size in the current implementation.

Current architecture:

```text
PR
 |
 v
BASE_SHA
 |
 +---- git diff ----+
                   |
                   v
             Changed Code
                   |
                   v
              AI Review
```

For larger repositories, the recommended future architecture is:

```text
Large PR diff
    |
    +--> File classification
    |
    +--> Logical chunking
    |
    +--> Provider calls
    |
    +--> Merge findings
```

The current implementation limits the diff size; production evolution should prefer logical chunking rather than silently dropping important changes.

## 10. Node.js Review Component

Node.js acts as the application layer between GitHub Actions and Gemini.

Its responsibilities include:

- Reading the review rules.
- Receiving the PR diff.
- Building the review prompt.
- Selecting the model.
- Reading the API key from the environment.
- Calling Gemini.
- Handling API failures.
- Extracting the review response.
- Calculating the review result.

The architecture intentionally keeps provider-specific API handling inside the provider adapter.

---

## 11. Gemini Configuration

The current implementation uses:

```text
Provider: Gemini
Model: gemini-3.6-flash
```

The configured API flow is:

```text
GitHub Actions
      |
      v
Node.js
      |
      | GEMINI_API_KEY
      v
Gemini generateContent
      |
      v
Gemini review text
```

The current endpoint is:

```text
https://generativelanguage.googleapis.com/v1beta/models/${model}:generateContent
```

Authentication is supplied using:

```text
x-goog-api-key
```

The model identifier is configured in the Node.js implementation.

Model availability can change, so the configured model should be verified against the current provider documentation before a production rollout.

## 13. Gemini Response Processing

The current implementation receives natural-language review text.

Node.js processes the response and calculates severity counts:

```text
Critical
High
Medium
Low
```

The current recommendation logic is:

```text
totalIssues > 0
    |
    v
CHANGES REQUESTED

totalIssues == 0
    |
    v
APPROVE
```

This means the application, rather than Gemini's wording alone, controls the final recommendation.

---

## 14. Quality Gate

The quality gate is the deterministic CI/CD decision point.

The intended contract is:

```text
APPROVE
    |
    v
PASS

CHANGES REQUESTED
    |
    v
FAIL

Missing / malformed / unsupported
    |
    v
FAIL
```

This is called **fail-closed behavior**.

The quality gate should not search the complete natural-language review for a word such as:

```text
APPROVE
```

because that word can appear in explanatory text.

The target architecture is:

```text
AI
 |
 v
Validated / Normalized Result
 |
 +--> PR Comment
 +--> HTML Report
 +--> Email
 +--> Quality Gate
```

The application owns the final CI decision.

---

## 15. GitHub PR Comment

After the AI review is generated and processed, the workflow publishes the review back to the Pull Request.

Purpose:

- Give developers immediate feedback.
- Show findings against the PR.
- Make the AI review visible in the normal development workflow.

The PR comment is an output of the review process; it should not independently determine the quality-gate decision.

---

## 16. HTML Report

The workflow generates an HTML report containing the review information.

Purpose:

- Provide a detailed report.
- Make findings easier to read.
- Provide a report artifact/output separate from the PR conversation.

The recommended architecture is that the HTML report consumes the same normalized review result as the PR comment and quality gate.

---

## 17. Email Report

The workflow can also generate an email report.

The email path requires appropriate SMTP credentials.

Those credentials must be treated as secrets and stored securely.

The architecture principle is:

```text
Normalized ReviewResult
        |
        v
Email Generator
        |
        v
SMTP
        |
        v
Recipient
```

The email generator should not independently reinterpret the raw AI response.

The troubleshooting documentation identifies duplicated parsing in the email step as a source of inconsistencies and recommends passing the validated recommendation into email generation.

### Developer

## 19. End-to-End Example

Suppose a developer changes a Playwright test and creates a Pull Request.

### Step 1 — PR created

GitHub generates the Pull Request event.

### Step 2 — GitHub Actions starts

The `pull_request` workflow responds to the configured event.

### Step 3 — Repository checkout

The workflow obtains the repository source and history.

### Step 4 — Review rules loaded

`CODE_REVIEW.md` is read from the PR base commit.

### Step 5 — PR boundaries identified

The workflow identifies:

```text
BASE_SHA
HEAD_SHA
```

### Step 6 — Diff generated

The workflow generates:

```text
git diff BASE_SHA HEAD_SHA
```

The review policy and review workflow are excluded from the application diff.

### Step 7 — Prompt built

Node.js combines:

```text
Review rules
+
PR diff
+
Review instructions
```

### Step 8 — API key supplied

GitHub Actions exposes:

```text
GEMINI_API_KEY
```

to the required runtime step.

The key is not stored in the source code.

### Step 9 — Gemini called

Node.js calls the configured Gemini `generateContent` endpoint.

### Step 10 — Gemini reviews code

Gemini evaluates the changed code against the configured review rules.

### Step 11 — Response processed

Node.js receives the review and calculates severity counts.

### Step 12 — Recommendation generated

For the current implementation:

```text
Issues > 0
    -> CHANGES REQUESTED

Issues = 0
    -> APPROVE
```

### Step 13 — Review published

The review is made available through the PR/reporting flow.

### Step 14 — Quality gate

The workflow evaluates the recommendation.

```text
APPROVE
    -> PASS

CHANGES REQUESTED
    -> FAIL
```

### Step 15 — Developer fixes code

If changes are requested, the developer pushes another commit.

That generates a `synchronize` event and the review runs again.

## 22. Provider-Neutral Architecture

The project is designed so that Gemini is not permanently coupled to the rest of the review pipeline.

Conceptually:

```text
                   +--> Gemini
                   |
PR Review Input ---+--> OpenAI
                   |
                   +--> Other LLM
                         |
                         v
                 Normalized ReviewResult
                         |
              +----------+----------+
              |          |          |
              v          v          v
             PR        Email      Quality
           Comment      HTML       Gate
```

Provider-specific code should handle:

- Authentication.
- API request.
- Model.
- Provider response.

The rest of the workflow should consume a common result.

```json
      "severity": "HIGH",
      "file": "src/example.js",
      "line": 42,
      "problem": "Description",
      "why_it_matters": "Impact",
      "recommended_fix": "Fix"

  ],
  "recommendation": "CHANGES REQUESTED"

```

Valid values:

```text
severity:
CRITICAL | HIGH | MEDIUM | LOW

recommendation:
APPROVE | CHANGES REQUESTED
```

The normalized result should be consumed by:

```text
PR Comment
HTML Report
Email
Quality Gate
```

This eliminates multiple independent parsers.

## 25. Interview Explanation — 60 Seconds

A strong explanation of the project is:

> I built a GitHub Actions-based AI code-review quality gate for Pull Requests. When a developer creates, updates, or reopens a PR, GitHub Actions starts the workflow. The workflow checks out the repository, reads the repository-level `CODE_REVIEW.md` rules, identifies the PR `BASE_SHA` and `HEAD_SHA`, and generates the changed-code diff. The Node.js review component combines the rules and diff and sends them to Gemini using the `GEMINI_API_KEY` stored securely in GitHub Actions Secrets. Gemini returns the code-review findings, which the application processes into severity information and an `APPROVE` or `CHANGES REQUESTED` recommendation. The result is published back to the PR and can also generate HTML and email reports. Finally, the GitHub Actions quality gate makes the deterministic CI decision: approved reviews pass, requested changes fail, and invalid results fail closed.

## 27. Interview — Architecture Questions

### Why use GitHub Actions?

Because it provides an event-driven CI/CD environment that integrates naturally with the Pull Request lifecycle.

### Why use `BASE_SHA` and `HEAD_SHA`?

They provide deterministic boundaries for identifying exactly what changed in the Pull Request.

### Why use `CODE_REVIEW.md`?

It separates review policy from the application implementation and provides consistent instructions to the AI reviewer.

### Why use a provider adapter?

It isolates provider-specific authentication, API requests, models, and response formats from the rest of the framework.

### Why support multiple providers?

To reduce vendor lock-in and allow comparison of quality, cost, latency, and reliability.

### Why should AI not directly control CI?

Natural-language AI output is not a reliable control interface. Application code should validate the result and own the pass/fail decision.

### What is fail-closed?

If the result is missing, malformed, or unsupported, the pipeline fails instead of allowing the PR to pass.
